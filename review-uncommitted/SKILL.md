# Review Uncommitted Code

review 工作区未提交的代码。整个流程只读：只报告问题，不修改任何文件；除非用户明确要求修复，否则不要动手改代码。

## Step 1: 确定未提交范围

未提交 = 已暂存 + 未暂存 + 未跟踪，三者缺一不可：

```bash
git status --short    # 总览，确认三种状态各有哪些文件
git diff              # 未暂存改动
git diff --cached     # 已暂存改动
```

- 未跟踪文件（`??` 状态）没有 diff，直接读文件内容纳入审查。
- 改动很多时按目录/模块分组逐组审查；不要只看文件名就下结论。
- 若工作区没有未提交改动，直接告知用户并停止，不要转去 review 已提交历史。

## Step 2: 补齐上下文

审查前先读触达区域的局部约定，避免把项目既定风格当问题报：

- 仓库根的 `AGENTS.md` / `CLAUDE.md`
- 触达模块的架构、契约或矩阵文档（如 `docs/` 下相关文件）

## Step 3: 逐文件审查

对每个改动文件，读完整上下文（不要只看 diff hunk 附近几行），检查四个维度：

1. **正确性 / 回归**：是否引入预期之外的行为变化；边界条件、失败路径是否处理
2. **安全 / 隐私**：输入校验、注入、敏感信息泄漏、权限放大
3. **性能 / 可靠性**：热路径新增开销、重复计算、泄漏、竞态、缺少清理
4. **契约 / 测试**：调用方与被调方签名、类型是否同步；跨端契约是否被破坏；改动是否缺少对应测试

## Step 4: 输出格式

每条发现包含：`文件:行号`、严重程度（high / medium / low）、问题描述、为什么重要、修复建议，按严重程度排序。

- 只报有实际影响的问题；风格偏好和臆测性问题不报。宁可漏掉一个 nit，也不要淹没在噪音里。
- 没有实质问题时直接说改动是干净的，不要硬凑反馈。
- 结尾给一行结论：哪些必须改（fix now）、哪些建议改（fix soon）、哪些可以放过（optional）。

## 补充

- 改动量特别大（如整个功能分支叠加在工作区）时，可提示用户改用 `review-swarm`（并行子代理审查）分担。
